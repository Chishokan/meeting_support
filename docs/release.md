# バージョン管理とリリースの手順

## ブランチの使い分け

| ブランチ | 役割 | 公開先 |
|---|---|---|
| `main` | 本番。社員が毎日使う | meeting-support.vercel.app |
| `develop` | dev 環境。本番に出す前にまとめて確認する | meeting-support-dev.vercel.app |
| 作業ブランチ | 1つの機能・修正 | Vercel が自動で作るプレビューURL |

流れ：作業ブランチ → `develop`（dev 環境で確認）→ `main`（本番）

## バージョンの付け方

`0.2.0` のように「大.中.小」の3つの数字で表す。

| 上げる数字 | どんなとき | 例 |
|---|---|---|
| 大（1つ目） | 使い方が大きく変わる・データの形が変わる | 本認証への切り替え、全アプリの作り替え |
| 中（2つ目） | 機能や画面が増える | 総合画面の追加、門配管理の公開 |
| 小（3つ目） | 不具合の修正・文言の直しだけ | 表示崩れの修正 |

## 本番に出す手順

1. `develop` で変更を確認し終えたら、`package.json` の `version` を上げ、`CHANGELOG.md` の「未リリース」を日付に書き換える
2. `develop` → `main` のプルリクエストを作る（タイトル例：「リリース v0.2.0」）
3. 本番に出してよいか確認してからマージする
4. マージしたら、GitHub の **Actions → 「リリースタグを付ける」→ Run workflow** を実行する
   - `Use workflow from` は `main`。入力は空のままでよい
     （`package.json` の version からタグ名を作るので、画面に出るバージョンと必ず一致する）
   - リリースノートは `CHANGELOG.md` の同じバージョンの節がそのまま入る
   - 初めてのときは「お試し実行」にチェックを入れると、何も作らずに内容だけ確認できる
   - 手で付けたいときは GitHub の Releases からでも可（タグ名の入力を忘れないこと）
5. 本番のメニュー画面の下（会議DXでは左メニューの下）に出るバージョンが新しくなっていることを確認する

## 急ぎの修正（本番の不具合）

1. `main` から作業ブランチを作って修正し、`main` にプルリクエストを出す
2. 小の数字を上げる（例：0.2.0 → 0.2.1）
3. マージしてタグを付けたら、`main` を `develop` にも取り込む（取り込み忘れると、次のリリースで修正が消える）
