# 智翔館 会議DX ─ 知識ベース（外部DB）構成案

このドキュメントは「AIが社内資料を参照してQA回答する」ための
① データ構成 ② 導入工程 の設計案。実装前の合意用。

---

## 0. 前提（現状の棚卸し）

現行アプリで既に動いているもの:

| 機能 | 保存先 | 経路 |
|---|---|---|
| 問い合わせ | スプレッドシート「問い合わせ」 | Apps Script `saveInquiry` / `listInquiries` |
| 数値報告 | スプレッドシート「夏期数値」 | `saveNumbers` / `listNumbers` |
| 成功事例 | スプレッドシート「成功事例」 | `saveSuccess` / `listSuccess` |
| 中間報告 | スプレッドシート「中間報告状況」 | `appendProgress` / `listProgress` |
| 議事録 | Google ドキュメント | `saveMinutes` |
| 会社の前提知識 | `lib/companyKnowledge.ts`（ハードコード19行） | プロンプトに直接埋め込み |

**課題**: 知識が `companyKnowledge.ts` の19行しかない。
理念・規程・マニュアル・イベント要項・過去の議事録などは
Drive／ローカル／個人PCに散在し、AIから参照できていない。

---

## 1. 基本方針：入力層と検索層を分ける

```
┌─────────────────────────────┐
│ 入力層（正本）                                                │
│ Google ドライブ / スプレッドシート                            │
│ 各部門担当者がいつも通り書く。形式は Excel/Word/PDF/JPEG 混在可 │
└──────────────┬──────────────┘
               │ Claude タスク（定期実行）が変換・要約・索引化
               ▼
┌─────────────────────────────┐
│ 検索層（写し・読み取り専用）                                   │
│ Git リポジトリ `knowledge/` … Markdown + front matter          │
│ Vercel のビルドに同梱されるので認証なし・高速・grep 可能        │
└──────────────┬──────────────┘
               │ Claude API（tool use）が索引→ファイルの順に閲覧
               ▼
        QA 回答（出典パス付き）
```

**なぜ2層か**

- 人間にフォルダ運用を強制すると必ず破綻する。担当者はDriveから離れられない。
- AIが毎回 Drive API で Excel/PDF/JPEG を解析するのは、遅い・高い・不安定。
- Git に置けば差分がPRで見える。「誰がいつ理念を書き換えたか」が残るのは
  人事・方針まわりの資料では決定的に重要。

**動的データは検索層に同期しない**。数値報告・問い合わせ・イベント実績など
日々変わるものは、実行時に Apps Script API を叩く（既存の仕組みをそのまま使う）。
Git に入れると更新のたびに再デプロイが走ってしまう。

---

## 2. 置き場所の比較

| 候補 | 判定 | 理由 |
|---|---|---|
| **Google ドライブ** | **◎ 入力層として採用** | 現業と一致。共有・権限・同時編集が既にある。単独では検索が弱い |
| **Git リポジトリ** | **◎ 検索層として採用** | バージョン管理／grep／デプロイ同梱。バイナリ・個人情報は入れない |
| X サーバー | △ バックアップ専用 | Next.js の運用は困難。夜間ミラー（tar.gz）の退避先に留める |
| ローカルPC | ✕ 不採用 | 常時起動が前提になり単一障害点。止まると全社のAIが答えられない |
| ベクトルDB（Pinecone等） | 保留 | 最初は入れない。索引＋ファイル閲覧で走り、精度が頭打ちになってから検討 |

### X サーバーの使いどころ

今回の知識ベース本体には使わない。ただし以下は妥当:

- `knowledge/` と Drive の夜間バックアップ置き場（世代管理付き）
- 大きめPDF（パンフレット等）の静的配信。Git にバイナリを積まずに済む

## 3. フォルダ階層

Drive と Git で**同じ階層名**を使う。人間とAIが同じ地図を見られる状態を保つ。

```
knowledge/
├── 00_index/                      ← 第1フォルダ。AIが必ず最初に読む
│   ├── README.md                  ← 階層の説明・命名規約・更新ルール
│   ├── CLAUDE.md                  ← AIへの指示（回答方針・口調・禁止事項・出典の付け方）
│   ├── INDEX.md                   ← 全ファイル索引（自動生成）
│   └── GLOSSARY.md                ← 用語辞書（テ対外部・夏期外部・SYS/HYS/BS 等）
├── 10_理念・方針/
│   ├── 理念.md
│   ├── 社長方針_2026.md
│   └── 行動指針.md
├── 20_組織・人事/
│   ├── 組織図.md
│   ├── 職務分掌.md
│   └── 年間カレンダー.md
├── 30_部門/
│   ├── 31_小中等部/
│   ├── 32_RED個別/
│   ├── 33_高等部/
│   ├── 34_LEC/
│   └── 35_英検/
│       └── 各部門: 業務マニュアル / 料金 / カリキュラム / 校舎情報
├── 40_イベント/
│   └── 2026/
│       ├── 春期講習/    ← 要項・チラシ・実施記録・振り返り
│       ├── テスト対策会/
│       └── 夏期講習/
├── 50_問い合わせFAQ/              ← 過去の問い合わせ回答から育てる
│   ├── 保護者対応.md
│   ├── 社内手続き.md
│   └── システム操作.md
├── 60_規程・手続き/
│   ├── 就業規則_要約.md
│   ├── 経費精算.md
│   └── 各種申請フロー.md
└── 90_archive/                    ← 旧年度。索引には載せるが優先度を下げる
```

**命名規約**

- 数字プレフィクスで並び順を固定（`10_` `20_` …）。間に挿す余地を残して10刻み
- 年度が絡むものは `_2026` を末尾に
- 1ファイル1トピック、目安 200〜800行。長すぎると回答が薄まる

### front matter（全ファイル必須）

```yaml
---
title: 夏期講習会 実施要項 2026
dept: 小中等部            # 全社 / 小中等部 / RED個別 / 高等部 / LEC / 英検 / 総務
owner: 安東瑞輝           # 更新責任者
updated: 2026-06-01
source: drive:1AbcDEf...  # 原本の Drive ファイルID（再取得・リンク提示用）
source_type: spreadsheet  # doc / spreadsheet / xlsx / docx / pdf / image
tags: [夏期講習, 外部生募集, 要項]
visibility: all           # all / admin_only
summary: 2026年度夏期講習の日程・料金・外部生募集条件をまとめたもの
---
```

`visibility: admin_only` は総務部門ログイン時のみ索引に載せる。
**給与・評価・個人情報は Git に入れない**。必要なら Drive 直参照に限定する。

### INDEX.md（自動生成）

AIが最初に読む地図。本文は含めず、どのファイルを開くべきか判断させる。

```markdown
| パス | 部門 | 更新日 | 要約 | タグ |
|---|---|---|---|---|
| 10_理念・方針/理念.md | 全社 | 2026-04-01 | 智翔館の理念と大切にする価値観 | 理念,行動指針 |
| 40_イベント/2026/夏期講習/要項.md | 小中等部 | 2026-06-01 | 日程・料金・外部生募集条件 | 夏期講習,募集 |
```

## 4. 同期パイプライン（Claude タスクで定期実行）

```
① Drive スキャン    ─ 対象フォルダを走査し、更新日時とハッシュで差分検出
② 変換             ─ 形式ごとに Markdown 化
                      Google Docs → MD（Drive API export）
                      スプレッドシート → MD 表 or CSV（シート名ごと）
                      Excel/Word    → MD（xlsx / mammoth）
                      PDF           → テキスト（pdftotext、失敗時 Claude に画像で渡す）
                      JPEG/PNG      → Claude で説明文＋文字起こし
③ front matter 付与 ─ title/summary/tags は Claude が本文から生成、
                      owner/dept はフォルダ位置とDrive所有者から推定
④ INDEX.md 再生成   ─ 全 front matter を集約
⑤ 品質チェック      ─ 変換失敗・空ファイル・重複を検出しレポート
⑥ commit & push     ─ 差分があるときだけ。Vercel が自動デプロイ
```

**実行頻度**

| 対象 | 頻度 |
|---|---|
| 部門フォルダ・イベント | 日次（深夜） |
| 理念・規程 | 週次 |
| 全件ハッシュ再検証 | 月次 |

**変更は必ずPR経由**にして、理念・規程の書き換えは総務のレビューを通す。
部門マニュアル程度なら自動マージで良い。

## 5. QA の動き方

ベクトル検索は使わず、**索引 → ファイル閲覧**の2段構え（tool use のエージェントループ）。

```
質問「夏期講習の外部生の料金は？中3の場合」
  ↓
[system] CLAUDE.md + GLOSSARY.md + INDEX.md（索引のみ・本文なし）
  ↓
Claude が判断 → tool: read_file("40_イベント/2026/夏期講習/要項.md")
  ↓ 足りなければ tool: grep_knowledge("外部生 料金")
  ↓ 動的な数字が要るなら tool: get_numbers(dept="小中等部")  ← Apps Script API
  ↓
回答 ＋ 出典（フォルダパス と Drive リンク）
```

**AIに渡すツール**

| ツール | 用途 | 実装 |
|---|---|---|
| `read_file(path)` | ファイル本文を読む | Git 内ファイル読み込み |
| `grep_knowledge(query)` | 全文検索（索引で当たらない時の保険） | ripgrep 相当 |
| `list_dir(path)` | 階層を見る | fs |
| `get_numbers(dept)` | 数値報告の最新値 | 既存 `listNumbers` |
| `get_inquiries(keyword)` | 過去の問い合わせ回答 | 既存 `listInquiries` |

**設計上の要点**

- **INDEX.md は毎回プロンプトに入れて prompt cache に載せる**。数百ファイルでも数千トークンで収まり、キャッシュが効けばコストはほぼ無視できる
- **出典必須**。パスを示せない情報は回答させない。ハルシネーション対策として最も効く
- **わからない時は「わからない・誰に聞くべきか」を返す**。無理に答えさせない
- 回答できなかった質問をログに蓄積 → 月次で知識の穴を埋める

## 6. 権限

| レベル | 見える範囲 |
|---|---|
| 一般職員 | `visibility: all` のみ |
| 部門責任者 | 上記＋自部門の `admin_only` |
| 総務・人事・支援・管理 | 全て |

現在の認証は氏名＋部門＋合言葉の簡易版（`lib/auth.ts` は署名なしBase64）。
知識ベースに機微情報を載せる前に **Google SSO への移行が前提条件**。
それまでは `admin_only` を作らず、機微情報は Git に置かない運用にする。

## 7. 導入工程

各フェーズの終わりに「動くもの」が出る順に並べている。

### Phase 0：棚卸しと規約決定（1週間）

- [ ] 現在の資料の所在を一覧化（Drive／ローカル／紙）
- [ ] フォルダ階層と命名規約を確定（本書 §3 をたたき台に）
- [ ] 各フォルダの更新責任者（owner）を決める ← **ここが最重要。担当者不在のフォルダは必ず腐る**
- [ ] `00_index/` の4ファイルを手書きで作成

**完了条件**: 空でも階層が Drive 上に存在し、責任者が決まっている

### Phase 1：初期投入（2週間）

- [ ] 既存資料を階層へ移動（まずは「理念」「部門マニュアル」「今年度イベント」の3系統に絞る）
- [ ] `lib/companyKnowledge.ts` の19行を `10_理念・方針/` へ移し、実際の理念で肉付け
- [ ] 手動で Markdown 化し Git に投入（この時点では自動化なし）
- [ ] `INDEX.md` を手書き

**完了条件**: 30〜50ファイル程度が `knowledge/` に入り、grep で引ける

### Phase 2：QA を先に動かす（2週間）

同期の自動化より **QA を先に作る**。何が足りないかは動かさないと分からないため。

- [ ] tool use 版 QA API（`app/api/qa/route.ts`）
- [ ] `read_file` / `grep_knowledge` / `list_dir` ツール
- [ ] 既存の問い合わせ画面から呼べるようにする
- [ ] 想定質問 **50問の評価セット**を作成し正答率を測る

**完了条件**: 50問中35問以上に出典付きで正答

### Phase 3：同期の自動化（2週間）

- [ ] Drive スキャン＋差分検出
- [ ] 形式別コンバータ（Docs / Sheets / xlsx / docx / PDF / 画像）
- [ ] front matter・summary の自動生成
- [ ] `INDEX.md` 自動生成
- [ ] Claude タスクで日次実行、PR 作成

**完了条件**: Drive を更新した翌朝、AIの回答に反映されている

### Phase 4：社内ベータ（2週間）

- [ ] 総務＋各部門1名の計6〜7名で試用
- [ ] 回答不能ログを毎日確認し、知識の穴を埋める
- [ ] 評価セットを100問へ拡張

**完了条件**: 正答率80%以上、明らかな誤答ゼロ

### Phase 5：全社展開と運用（継続）

- [ ] 全職員へ公開
- [ ] 月次で「回答できなかった質問」レビュー→知識補充
- [ ] 四半期で階層の見直し（`90_archive/` へ退避）
- [ ] X サーバーへ夜間バックアップ

**目安：Phase 0〜4 で約9週間。**

## 8. 段階を踏むべきでない判断（先に決めておくこと）

| 論点 | 先に決める理由 |
|---|---|
| 各フォルダの owner | 後から決めると誰も更新せず、半年で知識が古くなって信用を失う |
| 出典必須のルール | 後から入れると「出典を出せない過去の回答」が残る |
| 個人情報を Git に入れない方針 | 一度入れると履歴から消すのが極めて面倒 |
| Google SSO への移行時期 | 機微情報を扱い始めてからでは遅い |

---

## 9. コスト感

- QA 1回あたり: INDEX（キャッシュ）＋読み込みファイル2〜3本 ≒ 数円
- 同期タスク: 日次で差分のみ変換。初回全件変換だけ重い
- ベクトルDB不要のため、外部サービス費用は当面ゼロ
