# 適性検査アプリ 設計書

2026-10-08 ／ 元資料：「適性検査 仕様分析・開発要件書」（@冨松太一）

現行の「塾講師適性検査」（Zinzycle社の受託システム、100問・はい/いいえ・A/B/C判定）を、智翔館アプリ（このリポジトリ）に
「適性検査」アプリとして移植する。講師（学生パート講師）だけでなく、**事務スタッフ・社員**も判定できるようにする。

## 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| 設問 | 現行の100問（許諾済み）をそのまま移植。10尺度×10問、一の位で尺度が決まる | 要件書どおり。本文は設問PDFから取り込み済み |
| 職種別の判定 | **設問は100問共通**。職種（講師／事務／社員）ごとに判定基準（尺度の重み・注意の閾値・面接の確認ポイント）を切り替える | 同じ回答から職種ごとの向き不向きを出せる。設問セットを3つ持つと同じ中身が3重になる |
| 閲覧できる人 | 管理部門（総務・人事・支援・管理）のみ | 性格検査の結果は機微な個人情報。lib/aptitude/access.ts の1か所で変えられる |
| 受検URLの届け方 | 画面で発行 → コピーして LINE WORKS・メール等で担当者が送る | アプリにメール送信の仕組みが無い。追加の契約・設定が要らない |
| 保存先 | Supabase（門配管理と同じ chishokan_dev／chishokan_prod）。手元の開発だけ .data/aptitude.json | 個人情報を1件1行で持つためスプレッドシートは使わない |
| 判定の扱い | あくまで面接の参考資料。画面に常に明記。判定だけで不採用を自動決定する機能は作らない | 要件書の非機能要件 |

## 尺度と採点

尺度コードは固定（コードで持つ）、名前・説明は版ごとに編集できる。

| 一の位 | コード | 尺度 | 種別 |
|---|---|---|---|
| 1 | L | 虚偽（ライスケール） | 信頼性 |
| 2 | CP | 批判的親（規範・責任感） | エゴグラム |
| 3 | NP | 養育的親（共感・世話好き） | エゴグラム |
| 4 | A | 大人（論理・計画） | エゴグラム |
| 5 | FC | 自由な子ども（感情表現・好奇心） | エゴグラム |
| 6 | AC | 順応した子ども（遠慮・他者評価への過敏さ） | エゴグラム |
| 7 | ST | ストレス耐性 | 適性 |
| 8 | EM | 情緒不安定・攻撃性 | リスク |
| 9 | AV | 対人回避 | リスク |
| 0 | IM | 未成熟・子ども志向 | リスク |

- **反転項目**：初期値は全問「はい＝1点」。回答用紙が「行＝尺度」で ○ を数えれば手採点できる作りのため。
  ストレス耐性の 17・57・97（投げ出す選択肢／無理に明るくしない／人に頼る）は「柔軟な対処」とみて加点にしたが、
  反転の可能性があるので設問マスタの備考に「要確認」と付け、マスタ画面から反転フラグを切り替えられるようにする
- **公正採用選考**：10・20・90・100（異性観・家族）は備考に「要確認」と付け、マスタ画面で ⚠ を出す。
  新しい版で「使わない」にできる（使わない設問は採点から外し、尺度の満点を減らして10点満点に換算する）

### 判定（lib/aptitude/scoring.ts・純粋関数）

1. 尺度得点：加点方向の回答を1点。使う設問数が10未満なら10点満点に換算
2. 適性スコア（0〜100）＝ Σ(重み×尺度得点) ÷ Σ(重み×10) × 100。重みは職種ごとに決める
3. 基本判定：適性スコアが A基準以上→A、B基準以上→B、それ未満→C
4. リスク：尺度ごとの「注意」「要注意」の閾値。注意に当たれば判定はBまで、要注意に当たればC
5. 信頼性（判定は変えず「参考値」と表示）：虚偽が閾値以上／平均回答秒数が下限未満（Web受検のみ）
6. 判定理由（どの数字でどう決まったか）と面接の確認ポイント（尺度が高い／低いときの質問例）を返す

職種ごとの初期値（**暫定**。過去の判定・入社後の評価と突き合わせて校正する前提）：

| | 講師（学生パート） | 事務スタッフ | 社員 |
|---|---|---|---|
| 重み | NP1.5・ST1.5・CP1・A1・FC1 | CP1.5・A1.5・NP1・ST1・FC0.5 | CP1.5・A1.5・ST1.5・NP1・FC1 |
| A/B基準 | 60／40 | 60／40 | 60／40 |
| 情緒不安定 注意/要注意 | 6／8 | 6／8 | 5／7 |
| 未成熟・子ども志向 | 3／5 | 4／6 | 3／5 |
| 対人回避 | 7／9 | 8／— | 7／9 |
| 虚偽（参考値） | 7以上 | 7以上 | 7以上 |
| 平均回答秒数の下限 | 1.0秒 | 1.0秒 | 1.0秒 |

結果は「受検したときの職種」で判定して保存する（使った版・計算日時も残す）。詳細画面では同じ得点を
他の2職種の基準で見た判定も並べて出す（保存はしない）。

## 画面

職員側（ログイン必須・管理部門のみ。メニューに「適性検査」カードを足す）

| URL | 内容 |
|---|---|
| /aptitude | 受検者一覧。拠点・職種・判定・受検状態・採用結果で絞り込み、氏名検索、登録日の新しい順。受検者の登録、校正用CSV |
| /aptitude/c/[id] | 受検者の詳細。プロフィール編集、受検URLの発行・コピー・取消・延長、紙回答の入力（10×10）、結果（エゴグラム折れ線・尺度バー・判定・理由・確認ポイント・他職種の判定）、採用結果と入社後評価、閲覧ログ |
| /aptitude/history | 受検履歴。受検日時・拠点・氏名・職種・方法・状態で絞り込み |
| /aptitude/master | 設問・尺度・判定基準の版管理。公開中の版は読み取り専用。「コピーして下書き」→編集→「公開」 |

受検者側（ログイン不要）

| URL | 内容 |
|---|---|
| /exam/[token] | 説明と同意（利用目的・保存期間）→ プロフィール確認（フリガナ・生年月日・電話・メール）→ 1画面10問 × 10ページ（進捗バー、全問回答で次へ、ページごとに保存＝途中から再開できる）→ 完了。得点・判定・尺度名は出さない |

- 表示順は受検ごとにランダム（尺度が推測されにくいように）。受検者のブラウザには設問番号を渡さず、
  「何番目に出したか」だけでやり取りする
- 受検URLの有効期限は既定7日。期限切れ・取消・受検済みはその旨を出す

## 権限・監査・保存期間（F10）

- 閲覧・操作は管理部門のみ（画面のレイアウトと全 API の両方で確かめる）
- 結果の閲覧・CSV出力・紙回答の入力・削除・版の公開を apt_logs に残す。詳細画面に「閲覧ログ」を出す
- 保存期間（lib/aptitude/model.ts の RETENTION）：
  - 採用結果が「不採用」「辞退」になってから **365日** で受検者・受検・回答・結果を削除
  - 画面で「削除」した受検者は **30日** 後に完全に削除（それまでは一覧から消えるだけ）
  - 実行：Vercel Cron が毎日 3:00（JST）に /api/aptitude/purge を叩く（CRON_SECRET。問合せ管理の cron と同じ仕組み）
- 受検者の同意（利用目的・保存期間）を受検前に取り、同意日時を残す

## 校正用CSV（F09）

受検ごとに1行：受検者ID・職種・拠点・受検日・方法・版・10尺度の得点・適性スコア・判定・フラグ・平均回答秒数・
採用結果・入社後評価（1〜5）・評価メモ。**氏名・連絡先は入れない**（校正に要らない）。

## 作らないもの

- メールの自動送信、受検者自身による受検申込（URLは職員が発行する）
- 現行システムの過去916件の取り込み（Zinzycle社にCSV出力の可否を問い合わせ中）
- 判定結果の受検者への開示

## 実装の順番

1. lib/aptitude：model（型・定数・入力チェック）／seed（v1の設問・尺度・判定基準）／scoring（採点）＋テスト
2. lib/aptitude/store（Supabase と手元の JSON を同じ口で扱う小さな層）＋ SQL
3. API：職員側（受検者・受検・マスタ・CSV・保存期間）／受検者側（/api/exam/[token]）
4. 画面：一覧・詳細（結果チャート・紙回答）・履歴・マスタ／受検画面
5. メニューのカード、README・supabase/README・CHANGELOG、vercel.json の cron
